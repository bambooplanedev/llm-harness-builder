# Набір вправ

Три короткі вправи на одній маленькій задачі, `slug`: виправити однорядкову помилку в
`src/slugify.js`, щоб пройшов `node --test`. Кожна займає від 10 до 40 хвилин.

| вправа | що ви робите | що потрібно |
|---|---|---|
| [1. Чому прогін упав](01-why-it-failed/README.uk.md) | прочитати записаний невдалий прогін і знайти, що робить інакше харнес, який проходить | лише Node, без моделі |
| [2. Хай bare пройде](02-make-bare-pass/README.uk.md) | змінювати один файл харнесу, доки `bench` з ним не пройде | модель, локальна чи в хмарі |
| [3. Повтор ходу](03-replay-a-turn/README.uk.md) | надіслати записаний хід ще раз і подивитися, чи модель піде тим самим шляхом | локальна модель; необов'язкова |

## Підготовка

### Локально

1. Node 22.12 або новіший, і llm-harness-builder 0.5.0 або новіший (`npx` бере найновіший): колонка
   `unanswered` в `analyze` і смуга складу запиту з'явилися після 0.4.0.
2. Ollama зі [сторінки завантаження](https://ollama.com/download); запустіть її, тоді:

       ollama pull qwen3:8b

3. У **порожній теці** (`serve` копіює харнеси з `harnesses/` пакета в теку, де його запущено):

       mkdir lab && cd lab
       npx llm-harness-builder serve

Для вправи 1 досить кроків 1 і 3 (на хості з інтерфейсом) або самого терміналу: у контейнері з розділу
«Безпека» її можна пройти повністю, див. шлях «Термінал» у вправі.

### У хмарі

Без GPU ті самі команди працюють на хмарному API, як у розділі
[Хмара](https://github.com/bambooplanedev/llm-harness-builder/blob/main/README.uk.md#хмара) в README.
Додайте до `bench` ці чотири прапорці:

    --kind openai --base-url https://openrouter.ai/api/v1 \
      --api-key-env OPENROUTER_API_KEY --model nvidia/nemotron-3.5-lightning:free

Досить безкоштовного акаунта OpenRouter: моделі, чий id закінчується на `:free`, нічого не коштують,
але OpenRouter дозволяє їм 20 запитів на хвилину і 50 на день. Безкоштовні моделі OpenRouter
з'являються й зникають: якщо цієї вже нема, оберіть будь-яку безкоштовну модель з підтримкою
інструментів. Хмарний API відхиляє `backend.think`. Усі локальні числа в цьому наборі — з qwen3:8b на
Ollama; єдиний хмарний рядок, у розв'язку вправи 2, — з названої там моделі OpenRouter. У хмарі ваші
числа будуть іншими.

### Безпека перед будь-якою вправою з моделлю

`bench` схвалює кожну команду, яку надсилає модель, і виконує її від вашого імені, з вашими файлами
і вашим оточенням. Тому:

- Запускайте його в контейнері. З теки `lab`:

      docker run --rm -it -v "$PWD":/work -w /work node:22.12-slim bash

  Ollama на хості тоді доступна як `--base-url http://host.docker.internal:11434` (на Linux додайте
  до `docker run` `--add-host=host.docker.internal:host-gateway`, а Ollama запустіть з
  `OLLAMA_HOST=0.0.0.0`, щоб контейнер міг до неї дістатися). Інтерфейс із контейнера
  недоступний, тож у контейнері проходьте вправу 1 повністю в терміналі (`npm init -y && npm i
  llm-harness-builder`, далі шлях «Термінал»), а шлях через інтерфейс лишіть для хоста: `serve` там
  не потребує моделі.
- Беріть ключ із лімітом витрат, створений саме для цього.
- Не тримайте в цьому оточенні жодних інших секретів.
- Ніколи не додавайте ключ у `tools.bashEnv`: так він дістанеться кожній команді, яку запускає модель.
- Безкоштовні провайдери можуть логувати ваші запити. Не надсилайте нічого, що не готові оприлюднити.

## Як читати трейс

**В інтерфейсі.** Під час першого відкриття, поки прогонів ще немає, **Почніть звідси** у списку
Runs відкриває записаний прогін PASS і прогін FAIL; **Examples** будь-коли відкриває приклад бенча,
де ці прогони є в списку, модель не потрібна. Прогін показує свої ходи: що надіслано, що повернулося,
кожен виклик інструмента і його результат. Смуга над ходами показує, з чого складався кожен запит
(системний промпт, описи інструментів, історія, результати інструментів), з «≈» там, де сервер не
надіслав usage. **Почніть звідси** відкриває також приклад бенча: натисніть `⇄` на одному з його
прогонів, щоб порівняти його з відкритим, — які ручки конфігу відрізняються, і шлях обох хід за
ходом з позначкою першого розходження.

**У терміналі.** `npx llm-harness-builder analyze <trace.jsonl | run-id | bench.json> ...` друкує
рядок на прогін. Id прогону шукається в `./runs`. Колонки:

- `harness`, `run`: назва харнесу та id прогону.
- `verdict`: чим закінчився прогін — `final` (модель відповіла), `aborted` (зупинено ззовні,
  наприклад тайм-аутом `bench`), `max_turns`, `parse_failed` тощо.
- `turns`: скільки запитів пішло до моделі.
- `stub@`: хід, на якому бюджет контексту вперше замінив старі результати інструментів стабом.
- `ate`: які результати інструментів прибрав цей стаб.
- `edit@`: хід першого редагування, яке застосувалося.
- `loop on`: файл із найбільшою кількістю невдалих редагувань, скільки разів його редагували чи
  переписували (`×4`), і невдачі за видами (`zero 2`: два редагування, чий текст `old` не знайшовся
  ніде). Колонку заповнено, лише коли файл має щонайменше два невдалі редагування, тож одне
  невдале редагування ще показує `—`.
- `reread`: перший раз, коли модель знову прочитала файл після того, як попереднє читання замінив стаб.
- `unanswered`: скільки останній запит прогону чекав і не дочекався відповіді.

`—` означає, що показувати нічого.

## Як себе перевірити

- Вправа 1: порівняйте свої відповіді з її [розв'язком](01-why-it-failed/solution.uk.md).
- Вправа 2: запустіть команду `bench`, яку дає вправа. Вправу зараховано, якщо з трьох прогонів
  PASS щонайменше два. Три прогони — це шум: для 2 з 3 інтервал Вілсона (95%) — 0.21–0.94, тож
  успіх каже, що файл може спрацювати, а не як часто.
- Вправа 3: порівняйте з її розв'язком.
